## 3. 스코프를 100건 수준으로 재조정

724건도 초기 파이프라인 검증엔 과하다고 판단, **회사당 가장 최근 사업보고서 1건**으로 최종 축소:

- `report_nm`이 `사업보고서 (YYYY.MM)` 패턴(원본/[기재정정]/[첨부정정]/[첨부추가] 포함)인 것만 필터링 — "해외증권거래소등에신고한사업보고서등의국내신고"처럼 이름에 "사업보고서"가 들어가지만 실제로는 다른 공시인 건 정규식으로 제외
- 회사별로 접수일(`rcept_dt`) 기준 최신 1건만 선택 — 정정본은 원본보다 항상 나중에 접수되므로 이 방식으로 자동으로 최신 정정본이 뽑힘
- 결과: **99개 기업 × 1건 = 99건** ([data/processed/latest_annual_reports.csv](../data/processed/latest_annual_reports.csv))
- 맥쿼리인프라(투자회사)는 사업보고서 형태로 공시하지 않아 대상에서 빠짐

생성 스크립트: [scripts/build_latest_annual_reports.py](../scripts/build_latest_annual_reports.py), 다운로드: [scripts/download_periodic_reports.py](../scripts/download_periodic_reports.py) → `data/raw/documents/{rcept_no}.zip`

## 4. 원본 문서 구조 파악

삼성전자 사업보고서(rcept_no=20250311001085)로 원본 zip을 까본 결과:

- zip 안에 XML이 여러 개 들어있음 — 본문 1개(5.78MB) + 첨부 감사보고서/재무제표(별도·연결 각 500~600KB)가 별개 파일로 붙어있는 경우가 있음 (회사/보고서에 따라 1~3개)
- 본문 XML은 DART 자체 DTD 기반 구조화 문서: `SECTION-1/2/3`(목차 계층) > `TITLE` + `P`(문단) + `TABLE`(표, 문서당 최대 2,000개 이상!)
- 표는 `TABLE > TBODY > TR > TD/TE/TU/TH` 구조로, 재무제표 등 숫자 데이터 대부분이 여기 들어있음

자세한 내용은 [docs/parsing.md](parsing.md) 참고.

## 5. 문서 길이 / 블록 통계 (99개 문서 전체, 원자료: `data/processed/eda_full_stats.json`)

- 파싱 후 블록(문단/표) 개수: 문서당 수백~수천 개, 총 342,529개 블록(문단 145,741 + 표 196,788)
- **문단 블록 길이**: 중앙값 47자, p90 251자, p95 364자, p99 801자, 최대 17,523자 → 대부분 매우 짧아서 여러 개를 묶어야 의미 있는 청크가 됨. 최댓값은 버그가 아니라 `<P>` 태그 없이 긴 문단이 통째로 이어진 실제 서술(재무제표 주석 등)임을 확인
- **표 블록 길이**: 중앙값 81자, p90 659자, p95 1,161자, p99 3,580자, **최대 269,698자(!)** → 최댓값도 실제 데이터(LG전자 연구개발실적 상세표 등 수백 행짜리 표)로 확인됨, 버그 아님. 청킹 시 반드시 분할 필요
- 최상위 섹션별 블록 분포: `III. 재무에 관한 사항`이 압도적으로 많음(119,804개, 전체의 ~35%) — `(첨부)연결재무제표`(64,407) + `(첨부)재무제표`(51,171)까지 합치면 재무 관련 섹션이 전체 블록의 절반을 넘음

## 6. 데이터 품질 이슈 (원본 XML 자체의 결함)

DART가 생성하는 XML 자체가 완전한 well-formed XML이 아닌 경우가 있었다. 99개 문서 전체를 실제로 파싱해보며 발견한 문제 3종 (전부 [docs/parsing.md](parsing.md)의 `_sanitize_xml()`로 해결):

1. **이스케이프 안 된 `&`**: 본문에 `Data & Solution`처럼 raw `&`가 그대로 들어있어 strict XML 파서가 그 지점에서 깨짐 (SK하이닉스 사업보고서에서 발견)
2. **장식용 꺾쇠괄호가 가짜 태그로 인식됨**: `<주요자회사>`, `<SK스퀘어>`, `<Wholesale 부문>`처럼 소제목에 홑화살괄호(〈〉) 대신 `<>`를 그냥 써버린 경우가 다수 발견됨(전수조사 결과(58개 후보 중) 진짜 DART 태그 33개 vs 나머지 25개는 전부 1~13회만 등장한 회사/사업 용어(장식 꺾쇠)). 닫는 태그가 없으니 파서가 그 지점부터 뒤 구조를 전부 잃어버리고, 최악의 경우 문서 나머지 전체가 하나의 거대한 문단 블록(수십만 자)으로 뭉개짐
3. **정정 공시 3건의 원본 문서가 DART에 아예 존재하지 않음**: `document.xml` API가 JSON이 아니라 `<result><status>014</status>...</result>` 형태의 **XML 에러**를 돌려주는데, `DartClient.get_bytes()`가 JSON 에러만 걸러내던 버그로 이걸 zip인 줄 알고 저장해버림. zip 매직바이트(`PK`)로 판별하도록 고치고, 실패한 3건([첨부정정]/[기재정정] 필드만 고친 공시라 본문 자체가 없는 것으로 추정)은 같은 회사의 바로 이전 정기공시로 대체

또한 별개로, `_sanitize_xml()` 구현 자체가 **문서당 몇 시간이 걸리는 성능 버그**(O(n²) — `<`를 만날 때마다 문자열 나머지 전체를 복사)를 갖고 있던 걸 발견해서 위치 기반 매칭으로 고쳤다. 자세한 경위는 [docs/parsing.md](parsing.md) 참고.
