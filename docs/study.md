# 공부 노트: 파싱/청킹 기법 개관

RAG 파이프라인을 위한 파싱/청킹 기법들을 정리한 참고 문서. 이 프로젝트가 실제로 어떤 조합을 왜 선택했는지는 [docs/parsing.md](parsing.md), [docs/chunking_strategy.md](chunking_strategy.md) 참고 — 이 문서는 그 배경이 되는 일반적인 기법 지형도.

## 파싱(Parsing) 기법

문서를 텍스트로 뽑아내는 단계. 원본 형식(구조 有/無)에 따라 접근이 갈린다.

| 기법 | 특성 | 어디에 좋은지 |
|---|---|---|
| **Plain flatten** (`get_text()`류) | 태그 다 제거, 순수 텍스트만. 빠르고 구현 1줄 | 구조가 중요하지 않은 짧은 문서. 우리가 처음에 썼다가 표 때문에 버린 방식 |
| **구조 보존 파싱** (structure-aware) | 제목/섹션/표를 태그 종류별로 구분해서 유지 | 계층이 뚜렷한 공식 문서. 우리가 쓰는 방식(`parse_report_blocks`) |
| **DTD/스키마 기반 파싱** | 문서가 자체 스키마를 갖고 있을 때 그 스키마를 그대로 활용 | 우리 케이스 정확히 이거 — DART가 SECTION/TITLE/P/TABLE이라는 자체 DTD를 씀 |
| **레이아웃 기반 파싱** (PDF용) | 좌표(x,y) 정보로 컬럼/표 영역을 추론 (pdfplumber, PyMuPDF, Unstructured hi_res) | 스키마가 없는 PDF — 좌표 없인 표인지 문단인지 알 방법이 없음 |
| **표 특화 파싱** (Camelot, Tabula) | 표만 따로 인식해서 CSV/markdown으로 직렬화 | 표 비중이 높은 정형 문서. 우리 `_table_to_text`도 이 철학의 축소판 |
| **VLM/멀티모달 파싱** (LlamaParse 등) | 비전 모델이 문서 이미지를 보고 통째로 markdown화 | 스캔본, 차트/도표가 많은 문서. 정확도 높지만 문서당 비용/속도 부담 큼 |
| **OCR 기반** | 이미지→텍스트 (Tesseract 등) | 종이 스캔 문서 |

우리 문서(DART XML)는 자체 DTD가 있는 케이스라 제일 좋은 선택지(구조 보존)를 그대로 쓸 수 있었던 거고, PDF/스캔본이었으면 레이아웃 기반이나 VLM 쪽으로 갔어야 했다.

## 청킹(Chunking) 기법

파싱된 텍스트를 검색 단위로 자르는 단계.

| 기법 | 특성 | 어디에 좋은지 |
|---|---|---|
| **고정 크기** (fixed char/token) | N자마다 기계적으로 자름. 제일 단순 | 프로토타입, 구조 없는 raw text. 문장 중간에서 잘릴 수 있음 |
| **오버랩 슬라이딩 윈도우** | 고정 크기 + 앞뒤 겹침(예: 50자)을 둬서 경계 문맥 보완 | 고정 크기의 단점(경계에서 문맥 끊김)을 완화하고 싶을 때 |
| **재귀적 분할** (LangChain `RecursiveCharacterTextSplitter`) | 문단→문장→단어 순으로 우선순위 구분자를 재귀적으로 시도 | 실무 범용 기본값. 구조 정보가 없어도 "그나마 자연스러운 경계"를 찾음 |
| **의미 기반** (semantic chunking) | 문장 임베딩 유사도가 급격히 떨어지는 지점을 경계로 | 주제 전환이 잦은 블로그/뉴스. 임베딩을 미리 계산해야 해서 비용↑ |
| **구조 기반** (heading/section 경계) | 문서의 제목 계층을 그대로 청크 경계로 사용 | 계층이 명확한 공식 문서(법률/매뉴얼/사업보고서). 우리가 쓰는 방식 |
| **표 특화** (헤더 반복 분할) | 표는 행 단위로만 자르고, 큰 표는 헤더를 반복하며 분할 | 재무제표처럼 표가 크고 많은 문서. 우리 `_split_table_text` |
| **Parent-Child(계층적)** | 검색은 작은 청크로, 반환은 상위 섹션 전체를 같이 줌 | 정밀 검색 + 풍부한 답변 컨텍스트 둘 다 필요한 법률/의료 QA |
| **LLM 기반** (agentic chunking) | LLM에게 "의미 단위로 나눠줘"라고 직접 시킴 | 품질이 제일 중요하고 소규모 corpus라 비용 감당될 때 |

## 우리 조합이 여기서 어디 위치하나

**DTD 기반 구조 파싱 + 섹션 경계 청킹 + 표 특화 분할**의 조합. 일반적인 "재귀적 분할"(범용 기본값)보다 훨씬 문서 특화된 방식인데, 그게 가능했던 이유는 DART 문서가 흔한 unstructured PDF가 아니라 잘 정의된 XML 스키마를 갖고 있었기 때문 — 스키마가 없는 문서였다면 이 정도 정밀한 구조 활용은 불가능했을 것.

**남은 문제**(청킹 파라미터 조정 단계에서 다룰 것): 지금은 표가 크든 작든(레이아웃용이든 진짜 데이터든) 다 독립 청크로 분리하고 있어서, "구조 기반 청킹"과 "고정 크기 청킹"을 섞은 하이브리드로 다듬어야 하는 상황 — 작은 표는 문단처럼 묶고, 큰 표만 표 특화 분할을 적용하는 식으로.

## 임베딩(Embedding) 기법/툴

청크를 벡터로 바꾸는 단계. "어떤 표현 방식을 쓰나"와 "어디서/어떻게 돌리나" 두 축으로 나뉜다.

### 표현 방식

| 기법 | 특성 | 어디에 좋은지 |
|---|---|---|
| **Dense (bi-encoder)** | 문장 전체를 고정 차원 벡터 하나로 압축. 의미 유사도 기반 검색 | 범용 시맨틱 검색. 우리가 쓰는 방식(bge-m3 dense) |
| **Sparse** (BM25, SPLADE, TF-IDF) | 단어(토큰) 단위 가중치 벡터, 대부분 0 | 정확한 키워드/고유명사(단어 단위) 매칭에 dense보다 강함. **단, 종목코드 같은 순수 숫자 문자열엔 방식에 따라 갈림** — BM25/TF-IDF(단어 단위 통계)는 잘 맞지만, SPLADE/bge-m3 같은 서브워드(BPE) 기반 신경망 sparse는 "005930"이 `00`/`59`/`30`처럼 흔한 숫자 조각으로 쪼개져서 변별력을 잃는다(실측 확인, [retrieval_strategy.md](retrieval_strategy.md) 참고) |
| **Multi-vector** (ColBERT류 late interaction) | 토큰마다 벡터를 따로 유지, 검색 시 토큰 단위로 매칭 후 합산 | 정밀도가 dense보다 높지만 저장공간/연산량 훨씬 큼 — 대규모 서비스에서 재순위(rerank) 단계에 주로 씀 |
| **Hybrid (dense+sparse fusion)** | 두 점수를 합쳐서(RRF 등) 최종 랭킹 | 의미 검색 + 키워드 정확도 둘 다 필요할 때. Elasticsearch/OpenSearch, Weaviate 등이 기본 지원 |
| **Cross-encoder (rerank용)** | 쿼리+문서를 같이 넣어 하나의 관련도 점수만 출력, 임베딩이 아니라 재순위 전용 | 1차 검색(dense) 결과 상위 N개를 정밀 재정렬할 때 — 검색 단계 자체엔 못 씀(쿼리마다 문서 전체와 페어로 돌려야 해서 느림) |
| **Instruction-tuned embedding** (e5-instruct, bge+instruction prefix) | "이 텍스트는 질문/문서 중 무엇인가"를 프롬프트로 알려주고 인코딩 | 쿼리와 문서의 성격이 다른 비대칭 검색(질문 짧고 문서 길 때) 정확도↑ |
| **Matryoshka 임베딩** | 벡터를 앞부분만 잘라써도 성능 저하가 완만하도록 학습 | 저장공간/속도가 중요할 때 차원을 유연하게 줄임(OpenAI text-embedding-3 계열이 지원) |

bge-m3는 사실 dense/sparse/multi-vector(ColBERT) 셋 다 한 모델에서 뽑을 수 있는 게 특징인데, 이번 단계는 구현 단순함과 pgvector 궁합을 위해 dense만 쓰기로 했다([docs/embedding_strategy.md](embedding_strategy.md) 참고). 필요해지면 같은 모델에서 sparse/multi-vector를 추가로 뽑아 하이브리드로 확장할 여지가 남아있다.

### 서빙 방식/툴

| 방식 | 특성 | 어디에 좋은지 |
|---|---|---|
| **로컬 모델 직접 서빙** (`sentence-transformers`) | 모델을 GPU/CPU에 직접 로드해서 인코딩. 우리가 쓰는 방식 | 자체 GPU 있고, 토큰당 API 비용을 피하고 싶을 때 — 우리 프로젝트의 비용 민감성에 맞음 |
| **`FlagEmbedding`** (BAAI 공식 라이브러리) | bge 계열 전용, dense뿐 아니라 sparse/multi-vector도 한 번에 뽑아줌 | bge-m3의 sparse/multi-vector 기능까지 쓰고 싶어지면 `sentence-transformers`보다 이쪽이 직접적 |
| **관리형 임베딩 API** (OpenAI, Cohere, Voyage) | 호출당 과금, 인프라 관리 불필요, 대체로 고성능 | GPU가 없거나 트래픽이 들쭉날쭉해 자체 서빙이 비효율적일 때. 문서 15만 청크 같은 대량 배치엔 비용이 누적됨 |
| **전용 임베딩 서버** (HF Text Embeddings Inference, vLLM) | 임베딩 전용 최적화 서버, 배치/큐잉 자동 처리 | 여러 서비스가 같은 임베딩 모델을 동시에 호출하는 프로덕션 환경 |

우리는 로컬 GPU(L4)가 있고 15만 개 이상 청크를 반복적으로 실험하며 임베딩해야 해서, API 과금형보다 로컬 `sentence-transformers` 서빙이 비용상 명확히 유리하다 — 이게 GPU/토큰 비용을 아끼자는 프로젝트 방침과도 맞다.

## 임베딩과 DB의 관계

이 둘은 역할이 서로 다르고, 항상 짝을 이룬다.

- **임베딩 = 변환.** 청크 텍스트 하나를 모델(bge-m3)에 통과시켜 1024개 숫자로 된 벡터를 뽑아내는 계산 단계. GPU를 쓰지만, 그 자체로는 아무것도 저장하지 않는다 — 결과는 계산이 끝나는 순간 메모리에만 존재한다.
- **DB(pgvector) = 저장소 + 검색 엔진.** 계산된 벡터(와 원본 텍스트)를 `chunks` 테이블에 영구히 저장하고, 나중에 "이 벡터와 가장 가까운 벡터들"을 빠르게 찾아주는 인덱스(HNSW)를 유지한다.

파이프라인으로 보면:

```
문서 zip → 파싱(블록) → 청킹 → [임베딩: 텍스트→벡터, GPU] → [DB: 벡터+텍스트 저장, 인덱싱]
```

검색(질의) 시점에는 순서가 살짝 다르다 — 사용자 질문도 똑같이 임베딩해서 벡터로 바꾼 다음, DB에 "이 벡터와 코사인 거리가 가장 가까운 청크 K개를 달라"고 쿼리한다(`ORDER BY embedding <=> :query_vector LIMIT k`). 즉 **임베딩은 텍스트를 "검색 가능한 숫자"로 바꾸는 단계이고, DB는 그 숫자들을 모아 빠르게 비교하는 저장소** — 임베딩 없이는 DB에 넣을 벡터가 없고, 벡터 DB 없이는 임베딩 결과를 검색에 쓸 방법이 없다.

## 벡터 저장소 선택지 비교 (왜 pgvector인가)

| 선택지 | 특성 | 장단점 |
|---|---|---|
| **pgvector** (Postgres 확장) | 기존 관계형 DB에 벡터 컬럼/인덱스만 추가 | 관계형 데이터(회사/공시)와 벡터를 **같은 DB, 같은 트랜잭션**에서 관리 — "특정 회사 + 특정 기간"처럼 필터와 벡터 검색을 SQL `WHERE` 절 하나로 결합 가능. 오픈소스/무료, 별도 인프라 불필요(우리도 docker 없이 apt로 postgres+확장만 설치), ACID/백업 등 postgres 생태계 그대로 활용. 단점: 수억~수십억 벡터급 초대규모 분산 처리엔 전용 벡터 DB보다 불리 |
| **전용 SaaS 벡터 DB** (Pinecone 등) | 완전관리형, 벡터 검색에 특화 | 인프라 관리 불필요, 대규모 확장 쉬움. 단점: 벤더 종속, 사용량 과금, 관계형 데이터는 별도 DB에 두고 join을 애플리케이션 레벨에서 해야 함(비용 민감 프로젝트엔 부담) |
| **전용 오픈소스 벡터 DB** (Milvus, Qdrant, Weaviate) | 벡터 검색 전용으로 설계, 분산/샤딩 지원 | 대규모(수억 벡터) + 고가용성에 최적화. 단점: 별도 서비스/인프라를 새로 띄우고 운영해야 함 — 이미 postgres를 쓰는 우리 스택엔 인프라가 하나 더 늘어나는 오버헤드 |
| **인메모리 라이브러리** (FAISS) | DB가 아니라 벡터 검색 알고리즘 라이브러리 | 매우 빠르고 가볍지만, 영속성/메타데이터 필터링/동시성 제어를 직접 구현해야 함 — 연구용 프로토타입에 적합, 서비스 백엔드로는 부적합 |
| **Elasticsearch/OpenSearch** | 텍스트 검색(BM25) + kNN을 한 엔진에서 기본 지원 | dense+sparse 하이브리드 검색을 처음부터 내장. 단점: 벡터 검색이 핵심 기능이 아니라 부가 기능이라 순수 벡터 검색 성능/튜닝 폭은 전용 DB보다 좁음 |

우리 규모(약 15만 청크, 100개 기업)는 pgvector가 불리해지는 "초대규모 분산" 구간과는 거리가 멀고, 오히려 Company/Disclosure/Chunk 관계형 스키마와 벡터를 한 DB에서 join하며 다룰 수 있다는 이점이 크다 — 그래서 별도 벡터 DB 없이 pgvector로 결정했다.

## 검색(Retrieval) 기법

저장된 청크 중 질문과 관련된 걸 찾아오는 단계. "후보를 어떻게 찾나" → "여러 방식을 어떻게 합치나" → "어떻게 더 정밀하게 다듬나" → "질문 자체를 어떻게 개선하나" → "구조를 어떻게 활용하나" 순으로 레이어가 쌓인다.

### 1차 후보 검색 방식

| 기법 | 특성 | 장점 | 단점 |
|---|---|---|---|
| **Sparse (BM25/TF-IDF)** | 단어 빈도+역문서빈도 통계로 점수 계산. 모델 불필요 | GPU 불필요, 구현/이해 쉬움, 고유명사·정확한 숫자/코드 매칭에 강함(단어 단위 통계라 "005930"도 그 자체로 하나의 항목) | 동의어·의역을 전혀 이해 못함("매출"과 "판매수익"을 다른 단어로 취급) |
| **Dense (bi-encoder)** | 문장을 벡터로 임베딩, 코사인 유사도로 검색 | 의미가 비슷하면 단어가 달라도 찾아냄, ANN 인덱스(HNSW)로 대규모에도 빠름 | 정확한 숫자/코드/고유명사 매칭은 은근히 약함, 임베딩 계산에 GPU 필요 |
| **Learned sparse (SPLADE, bge-m3 sparse)** | 신경망이 토큰별 중요도를 학습해서 예측 | BM25보다 문맥을 반영한 키워드 매칭(유의어도 어느 정도 커버), 한글 복합어(회사명·계정과목명)엔 실제로 잘 작동함(실측 확인) | BM25보다 계산 비용 큼(모델 추론 필요), 전용 인덱스 지원이 상대적으로 미성숙(pgvector 0.6.0도 아직 없음). **서브워드(BPE) 토크나이저 기반이라 순수 숫자 문자열(종목코드 등)엔 약함** — "005930"이 `00`/`59`/`30`처럼 모든 재무제표에 흔한 숫자 조각으로 쪼개져서 변별력을 완전히 잃는 걸 실측으로 확인함(우리 프로젝트 dense/sparse 후보 겹침 0/20으로 관찰) |
| **Multi-vector (ColBERT류 late interaction)** | 문장 전체가 아니라 토큰마다 벡터 유지, 토큰 단위로 매칭 | 세 방식 중 검색 정밀도가 제일 높은 편 | 저장공간(청크당 벡터 수십~수백 개)·연산량 훨씬 큼 — 1차 후보 검색보다는 재순위 단계에 주로 쓰임 |

### 후보 결합 방식 (하이브리드)

| 기법 | 특성 | 장점 | 단점 |
|---|---|---|---|
| **가중합 (weighted sum)** | `score = a*dense + b*sparse` | 직관적, 구현 쉬움 | dense(코사인, -1~1)와 sparse(내적, 범위 들쭉날쭉)의 점수 스케일이 달라서 가중치 튜닝이 필요하고 데이터셋마다 최적값이 달라짐 |
| **RRF (Reciprocal Rank Fusion)** | 점수가 아니라 각 방식에서의 **순위**만 보고 `1/(k+rank)`를 합산 | 점수 스케일을 신경 쓸 필요 없음, 튜닝 거의 불필요, 업계에서 하이브리드 검색 표준으로 흔히 씀 | 순위 정보만 쓰다 보니 "얼마나 더 관련 있는지" 정도(점수 차이의 크기)는 반영 못함 |
| **Cascade(2단계)** | 한 방식(보통 dense)으로 넓게 후보를 찾은 뒤, 그 후보군 안에서만 다른 방식(sparse 등)으로 재정렬 | 구현/연산 간단(후보군만 계산하면 됨) | 1차에서 아예 후보에 못 들어온 문서는 2차에서도 영원히 못 찾음 — sparse가 dense를 보완하는 원래 목적이 약해짐 |

### 재순위(정밀화)

| 기법 | 특성 | 장점 | 단점 |
|---|---|---|---|
| **Cross-encoder rerank** | 질문+문서 쌍을 통째로 모델에 넣어 관련도 점수 하나만 출력 | bi-encoder보다 훨씬 정밀(질문-문서 상호작용을 직접 봄) | 후보 하나하나마다 모델을 돌려야 해서 느림 — 1차 검색엔 못 쓰고 상위 N개만 재정렬하는 용도 |

### 질의(query) 처리 개선

| 기법 | 특성 | 장점 | 단점 |
|---|---|---|---|
| **Query expansion/rewriting** | 질문에 동의어나 관련어를 추가/치환 | 짧고 애매한 질문의 재현율(recall) 개선 | 잘못 확장하면 오히려 노이즈 추가 |
| **HyDE (Hypothetical Document Embeddings)** | LLM에게 "이 질문에 대한 가상의 답변"을 먼저 생성시키고, 그 답변 텍스트를 임베딩해서 검색 | 질문보다 문서에 더 가까운 형태라 dense 검색과 궁합이 좋음 | 질의마다 LLM 호출 1회 추가(비용/지연) |
| **Multi-query** | 질문을 여러 버전으로 재작성해 각각 검색 후 결과를 합침 | 한 표현으로 놓치는 걸 다른 표현으로 보완 | 검색 횟수만큼 비용 증가 |
| **Query decomposition** | 복잡한 질문을 하위 질문 여러 개로 쪼개서 각각 검색 | "A와 B를 비교해줘" 같은 멀티홉 질문에 강함 | 쪼개는 것 자체가 LLM 호출 필요, 파이프라인 복잡도↑ |

### 구조/메타데이터 활용

| 기법 | 특성 | 장점 | 단점 |
|---|---|---|---|
| **메타데이터 사전 필터링 (self-query)** | 질문에서 회사명/기간 등을 추출해 벡터 검색 전에 SQL `WHERE`로 후보를 좁힘 | 관계 없는 기업 문서가 원천 차단돼 정확도·속도 둘 다 개선 | 추출이 틀리면(회사명 오인식 등) 그 필터 자체가 결과를 그르침 |
| **Parent-child(계층적) 검색** | 검색은 작은 청크 단위로, 반환은 상위 섹션 전체를 같이 줌 | 검색 정밀도(작은 단위)와 답변 문맥 풍부함(큰 단위)을 동시에 확보 | 저장/조회 구조가 한 단계 더 복잡해짐 |
| **GraphRAG류** | 엔티티(회사-자회사, 회사-계열사 등)를 그래프로 미리 구축, 관계를 타고 검색 | "A사의 자회사들 실적은?" 같은 멀티홉 관계형 질문에 강함 | 그래프 구축 자체가 별도 파이프라인(엔티티/관계 추출) 필요 — 비용/복잡도 큼 |

### 반복형(에이전틱) 검색

| 기법 | 특성 | 장점 | 단점 |
|---|---|---|---|
| **Iterative/multi-hop (ReAct류)** | "검색 → 결과 보고 부족하면 재검색"을 LLM이 스스로 반복 | 한 번에 못 찾는 복잡한 질문(추론 여러 단계 필요)에 강함 | 질의당 LLM 호출·지연시간이 여러 번 발생, 비용 제일 큼 |

## 우리 프로젝트엔 뭐가 맞나

1차 후보 검색은 **dense(bge-m3) + learned sparse(bge-m3 sparse)**를 같이 쓴다 — 재무제표 표(정확한 계정과목/숫자)는 sparse가, 서술형 문단은 dense가 강점이라 서로 보완된다. 결합은 **RRF**(가중치 튜닝 부담 없음), 후보 찾기는 **각 방식을 독립적으로 top-N 찾은 뒤 합치는 방식**(cascade 아님) — cascade로 하면 sparse를 쓰는 원래 목적(dense가 놓친 키워드 매칭 보완)이 무력화되기 때문. 메타데이터 필터(`corp_name` 등)는 API 호출부에서 명시적으로 넘길 수 있게 열어두되, 질문에서 자동 추출(self-query)은 지금은 범위 밖.

**지금은 안 하는 것**(GPU/LLM 호출 비용이 늘어나는 방식들 — 나중에 답변 품질이 부족하면 추가 검토):
- Cross-encoder rerank — 후보마다 추가 모델 추론 필요
- HyDE/Multi-query/Query decomposition — 질의마다 LLM 호출 추가
- GraphRAG, Iterative retrieval — 파이프라인 복잡도와 비용이 가장 큼, 우리 질문 유형(대부분 단일 기업의 특정 항목 조회)엔 아직 과함

## RAG 평가(Evaluation) 기법/툴

"검색이 관련 있는 걸 찾았는가"와 "답변이 근거자료에 충실한가(hallucination 없는가)"를 각각 따로 측정해야 한다 — 검색이 나빠도 생성이 이상하게 말을 잘 지어내면 답변만 봐서는 문제를 못 찾고, 반대로 검색이 좋아도 생성이 근거를 무시하면 역시 답변만 봐서는 원인을 못 짚는다.

### 프레임워크/툴

| 툴 | 특성 | 장점 | 단점 |
|---|---|---|---|
| **RAGAS** | LLM-as-judge 기반. `faithfulness`(답변이 근거에 충실한가), `answer_relevancy`(질문에 맞는 답인가), `context_precision`/`context_recall`(검색된 문맥의 정밀도/재현율), `answer_correctness`(정답과 비교) 등 지표 제공 | 검색·생성을 분리해서 각각 채점, RAG 평가 사실상 업계 표준, LangChain/LlamaIndex 연동 쉬움 | 지표 대부분이 LLM 호출 1회 이상 필요(질문당 여러 번) — 판정용 LLM 비용/시간이 듦, 판정 LLM 품질에 따라 점수 신뢰도가 갈림 |
| **TruLens** | RAGAS와 유사한 "RAG Triad"(groundedness/context relevance/answer relevance) + 트레이싱·대시보드 제공 | 평가와 함께 실행 추적(observability)까지 한 번에 봄 | 역시 LLM-as-judge라 호출 비용 발생, 대시보드까지 쓰려면 설정이 RAGAS보다 무거움 |
| **DeepEval** | pytest 스타일로 RAG 지표를 `assert` 형태로 작성(CI에 넣기 좋음) | 기존 테스트 스위트에 자연스럽게 통합, RAGAS와 지표 구성 비슷 | 역시 LLM-as-judge 비용 구조는 동일 |
| **ARES** | LLM 판정 대신 소량의 사람이 라벨링한 데이터로 경량 분류기를 학습시켜 채점 | 학습 후에는 LLM 호출 없이 훨씬 저렴하게 대량 평가 가능 | 초기에 사람이 라벨링한 시드 데이터가 필요 — 우리처럼 아직 골드셋이 없는 단계엔 진입장벽 |
| **BEIR류 전통 IR 벤치마크** | Recall@k/NDCG/MRR 같은 전통 정보검색 지표를 표준 데이터셋으로 계산 | LLM 호출 없이 계산만으로 채점, 완전히 객관적·재현 가능 | 검색만 평가하고 생성(답변) 품질은 전혀 안 봄, 우리 도메인 전용 골드셋(질문-정답청크 쌍)을 직접 만들어야 함 |
| **BLEU/ROUGE/BERTScore** | 생성된 답변과 정답 답변 문자열을 비교하는 전통 NLG 지표 | 계산 빠르고 저렴, LLM 불필요 | 표현이 다르면(같은 숫자를 다른 문장으로 말해도) 점수가 낮게 나옴 — 우리처럼 "숫자가 맞는가"가 핵심인 도메인엔 안 맞음(문장 유사도 ≠ 사실 정확도) |
| **직접 구현한 결정론적 체크** | LLM 판정 대신 규칙 기반으로 채점(예: 생성된 답변에 나온 숫자가 검색된 청크 텍스트 안에 실제로 존재하는지 정규식으로 대조) | 비용 0, 완전히 결정론적(재현 가능), 재무 수치 도메인엔 오히려 LLM 판정보다 신뢰도 높음 | 범용성이 낮음 — 우리 도메인(표 기반 수치 답변)엔 잘 맞지만, 서술형 답변의 "말투가 자연스러운가" 같은 건 못 봄 |

### 골드셋(정답 데이터) 필요 여부

일부 지표는 정답(ground truth)이 있어야 계산되고(`context_recall`, `answer_correctness`), 일부는 없어도 된다(`faithfulness`, `answer_relevancy`, `context_precision`는 검색된 문맥과 답변만 보고 채점 가능 — "reference-free"). 골드셋이 없는 프로젝트 초기엔 reference-free 지표부터 쓰고, 골드셋은 점진적으로(직접 검증한 질문-정답 쌍을 하나씩 쌓아가며) 만드는 게 현실적이다.

### 검증 방법론 (RAG 구현 직후 실제로 적용한 사례)

프레임워크를 붙이기 전에, "답변이 그럴듯해 보인다"와 "답변이 실제로 맞다"는 다르다는 전제로 파이프라인을 직접 검증했다. 이때 쓴 4가지 검증 축은 그 자체로 재사용 가능한 방법론이라 정리해둔다.

**1. 소스 대조(source cross-check) — 답변의 근거를 소스까지 역추적한다.**
생성된 답변에 등장한 핵심 수치(예: 삼성전자 매출액 `333,605,938`)를 답변만 보고 믿는 대신, `SELECT ... WHERE text LIKE '%333,605,938%'`로 DB 원문 청크를 직접 조회해서 (a) 그 숫자가 실제로 존재하는지, (b) 여러 표(사업부문별/제품별/지역별 매출)에서 서로 다른 각도로 합산해도 같은 값이 나오는지(내적 일관성)까지 확인했다. 답변 텍스트 자체는 아무리 그럴듯해도 "증거"가 아니다 — 소스까지 내려가야 검증이다.

**2. 메커니즘 단위 테스트 — 최종 답변이 아니라 파이프라인 내부 구성요소를 검증한다.**
"검색+생성 전체가 맞았다"는 결과 하나로는 *어느 단계*가 맞았는지 알 수 없다. `corp_name` 필터처럼 파이프라인 내부의 특정 메커니즘을 떼어내서, `retriever.search(..., corp_name="SK하이닉스")`의 결과 전부가 실제로 SK하이닉스인지를 별도로 assert했다 — 필터가 조용히 무시되고 있어도 최종 답변은 우연히 맞을 수 있기 때문에, 전체 답변 품질과 별개로 각 구성요소를 독립적으로 검증해야 한다.

**3. 네거티브 테스트(adversarial test) — 정답이 있는 질문만 테스트하면 절반만 검증한 것.**
"자료에 있는 걸 잘 찾아오는가"만 확인하면 시스템이 답을 지어내는 성향까지는 못 잡는다. 그래서 일부러 자료에 없는 질문("삼성전자 대표이사의 개인 취미")을 던져서, 모델이 근거 없이 그럴듯한 답을 만들어내지 않고 "자료에서 찾을 수 없습니다"라고 정확히 거부하는지 확인했다. 성공 케이스만 테스트하는 건 검증의 절반이다.

**4. 이상치를 만나면 무시하지 않고 원인을 끝까지 추적한다.**
dense와 sparse 후보가 겹치는지 확인하다가 "20개 중 0개 겹침"이라는, 언뜻 괜찮아 보이는(서로 다른 걸 찾으니 하이브리드가 의미 있다는) 결과가 나왔다. 여기서 멈추지 않고 sparse 상위 결과를 원문 대조했더니 정작 질의어("005930")를 포함한 청크가 하나도 없었다 — 이 모순을 tokenizer 레벨까지 추적해서 서브워드 분절 문제(`00`/`59`/`30`)라는 진짜 원인을 찾아냈다. "지표가 그럴듯해 보인다"에서 멈추면 이런 구조적 결함은 영원히 발견되지 않는다.

**5. 교차 검증(replication) — 같은 검증을 다른 입력으로 반복해서 우연이 아님을 확인한다.**
삼성전자 하나만 확인하고 끝내지 않고, 완전히 다른 회사(SK하이닉스)로 같은 질문 유형("영업이익은 얼마인가")을 반복해서 같은 방식(소스 대조)으로 재검증했다 — 첫 번째 성공이 우연이나 그 회사 데이터의 특수성 때문이 아님을 확인하기 위함이다.

이 5가지는 나중에 짤 평가 코드(결정론적 사실 정합성 체크, 골드셋 Recall@k 등)의 밑그림이기도 하다 — 지금 손으로 한 걸 스크립트로 자동화하는 것뿐이다.

## 지금까지 쓴 모델 중 한국어 전용 vs 다국어 (실측 사례 포함)

이 프로젝트 전 단계에서 **한국어 전용으로 파인튜닝된 모델은 하나도 안 썼다** — 전부 다국어 모델(또는 모델이 아예 필요 없는 규칙 기반)이고, 한국어는 그 다국어 지원 범위 안에 포함되는 형태다.

| 단계 | 실제 사용 | 한국어 지원 수준 | 한국어 전용 대안(참고, 안 씀) |
|---|---|---|---|
| 파싱 | 없음 - 규칙 기반(BeautifulSoup+정규식) | 해당 없음 | - |
| 청킹 | 없음 - 규칙 기반(문자 수 계산) | 해당 없음 | - |
| 임베딩(dense+sparse) | `BAAI/bge-m3` | **다국어**(100개+ 언어, 한국어 포함) - 한국어 전용은 아님 | `ko-sroberta-multitask`, `KoSimCSE`, `KLUE-RoBERTa` 계열 |
| 검색 - BM25 | 모델 없음(통계), 정규식+조사 제거 휴리스틱 토큰화 | 진짜 형태소 분석이 아니라 근사치([docs/experiments.md](experiments.md) 참고 - 조사 미처리 시 recall 0%까지 떨어졌던 사례) | `kiwipiepy`/`mecab-ko` 같은 형태소 분석기로 토큰화하면 더 정확 |
| 재순위(rerank) | `BAAI/bge-reranker-v2-m3` (처음엔 `bge-reranker-base` 썼다가 교체) | **다국어**(bge-m3와 같은 백본) - 한국어 잘 됨 | - |
| 생성 | `Qwen/Qwen2.5-3B-Instruct` | 다국어 지원, 한국어 성능은 준수하나 한국어 전용 파인튜닝은 아님 | `EXAONE-3.5`(LG), `Solar-Ko`(Upstage), `KULLM`, `KoAlpaca` |

**실측으로 확인한 한국어 지원 차이 사례**: reranker를 처음 `bge-reranker-base`로 붙였더니 "삼성전자 매출액은 얼마인가요"라는 질문에 정작 "매출액" 청크(-2.06점)보다 무관한 "영업이익" 청크(4.63점)를 더 높게 채점하는 걸 발견했다 — `bge-reranker-base`는 중국어/영어 위주로 학습된 모델이라 한국어 변별력이 약하기 때문. 같은 BAAI의 다국어 버전인 `bge-reranker-v2-m3`(bge-m3와 같은 XLM-R 계열 백본)로 바꾸자 "매출액"(-0.18점)이 정확히 1위로 올라왔다 — **모델을 다국어로만 바꿔도 한국어 태스크 정확도가 확 달라질 수 있다**는 걸 직접 확인한 사례.

**한국어 전용 모델로 안 바꾼 이유**: (1) 다국어 모델(bge-m3/Qwen2.5)이 이미 한국어를 충분히 잘 지원하는 걸 이번 세션 실험들로 확인했고, (2) 한국어 전용 모델(EXAONE-3.5, Solar-Ko 등)은 보통 더 크고(디스크 여유가 이미 빠듯함) DART 재무 도메인에 특화된 것도 아니라서, 지금 병목(생성 단계의 문맥 내 숫자 선택 오류 - [docs/experiments.md](experiments.md) 실험 4)을 한국어 전용 모델로 바꾼다고 자동으로 해결된다는 보장이 없다.

## 우리 프로젝트엔 뭐가 맞나

**LLM-as-judge(RAGAS 등)를 기본 채점자로 쓰지 않는다** — 판정마다 LLM 호출이 드는데, 이미 GPU/디스크가 빠듯한 이 환경에서 평가할 때마다 판정용 LLM까지 추가로 돌리는 건 비용 부담이 크다. 대신:

1. **결정론적 사실 정합성 체크(직접 구현)를 1차 지표로**: 생성된 답변에 등장하는 숫자가 검색된 청크 텍스트에 실제로 존재하는지 정규식으로 대조 — LLM 호출 없이 "숫자를 지어내지 않았는가"를 바로 확인할 수 있고, 이미 이번 대화에서 삼성전자 매출액을 SQL로 직접 대조 검증한 것과 같은 원리를 코드로 자동화하는 것뿐이다.
2. **작은 골드셋(질문-정답청크 20~30개)을 직접 만들어 Recall@k/MRR 계산** — LLM 없이 검색 품질만 객관적으로 측정. DART 재무제표는 정답이 명확해서(회사당 매출액/영업이익 등) 골드셋 만들기가 상대적으로 쉽다.
3. **RAGAS는 판정 LLM을 우리 로컬 Qwen으로 지정해서 소규모 샘플(예: 20문항)에만 보조적으로 사용** — 결정론적 체크로 못 잡는 "답변이 자연스럽고 질문에 맞게 답했는가" 같은 정성적 측면을 가끔 점검하는 용도로만, 매번 돌리는 CI성 평가로는 안 씀.

이 조합이면 평가 비용을 거의 0에 가깝게 유지하면서도, 우리 도메인(정확한 재무 수치)에서 가장 중요한 "숫자를 지어내지 않았는가"를 가장 신뢰도 높은 방식(결정론적 대조)으로 잡아낼 수 있다.
