# 청킹 전략

구현: [src/chunking/chunker.py](../src/chunking/chunker.py) · 테스트: [tests/test_chunker.py](../tests/test_chunker.py) · EDA 근거: [docs/eda.md](eda.md), [docs/parsing.md](parsing.md)

## 입력

`parse_report_blocks()`가 만든 블록 리스트: `{"section_path": [...], "type": "paragraph"|"table", "text": "..."}`. 이미 문단/표가 구분되어 있고 목차 경로가 붙어있다는 게 전제.

## 왜 단순 글자수 자르기(fixed-size)로는 안 되나

1. **문단이 표보다 훨씬 짧다** — 문단 블록 중앙값 47자(p95 364자, 99개 문서 전체 실측), 그런데 임의로 N글자마다 자르면 문장/의미 단위가 아니라 아무 데서나 끊긴다.
2. **표는 행 단위 의미가 있다** — 한 행이 "매출액 | 1,748,877 | 1,699,923"처럼 그 자체로 완결된 사실이다. 글자수 기준으로 자르면 행 중간이 잘려서 숫자와 항목명이 분리될 수 있다.
3. **표 크기 편차가 극단적이다** — 표 블록 길이 중앙값은 81자인데 최댓값은 269,698자(LG전자 연구개발실적 상세표). 청크 하나에 표 전체를 넣으면 안 되는 경우와, 여러 개를 합쳐야 하는 경우가 공존한다.
4. **섹션이 다르면 다른 주제다** — "I. 회사의 개요"의 문단과 "III. 재무에 관한 사항"의 문단을 한 청크에 섞으면 임베딩이 흐려지고 검색 정밀도가 떨어진다.

## 전략

### 1. 문단(paragraph) 청크 — 섹션 내에서 묶어서 자르기

같은 `section_path`를 가진 연속된 문단 블록들을 순서대로 이어 붙이다가, 다음 중 하나에 걸리면 청크를 끊는다:

- 목표 크기(`target_chars`, 기본 900자)를 넘어설 때
- `section_path`가 바뀔 때 (예: "1. 회사의 개요" → "2. 회사의 연혁")
- **"진짜 데이터 표"**(아래 3번 참고) 블록을 만났을 때

목표 크기를 900자로 잡은 근거: 문단 중앙값(47자)의 약 20배 정도 묶어야 사업보고서 서술 단위(한 항목에 대한 설명)가 한 청크 안에 온전히 들어간다. 너무 크게 잡으면 한 청크에 서로 다른 항목이 섞여 검색 정밀도가 떨어지고, 너무 작게 잡으면 문맥이 부족해 LLM이 답변에 활용하기 어렵다.

### 2. 표(table) 청크 — 헤더를 유지하며 행 단위로 분할

큰 표는 문단과 섞지 않고 독립 청크로 만든다. 크기가 임계값(`table_max_chars`, 기본 1,500자) 이하면 표 전체를 청크 하나로. 넘으면 첫 행(헤더로 간주)을 유지한 채 나머지 행들을 임계값 단위로 나눠 여러 청크를 만들고, **각 청크 앞에 헤더 행을 반복**해서 붙인다 — 그래야 청크 하나만 검색됐을 때도 "이 숫자가 뭘 의미하는지" 헤더 없이 유실되지 않는다.

```
청크 1: 구분 | 2024 | 2023
       매출액 | 1,748,877 | 1,699,923
       ...(임계값까지)

청크 2: 구분 | 2024 | 2023   ← 헤더 반복
       ...(다음 행들)
```

임계값을 1,500자로 잡은 근거: 표 블록 p95가 1,161자 — 즉 95%의 표는 그대로 청크 하나로 들어가고, 나머지 롱테일만 분할 로직을 타게 된다. 한 행 자체가 임계값보다 큰 경우(예: 한 셀에 긴 서술이 들어간 R&D 실적표)는 행을 쪼개지 않고 그대로 하나의 청크로 둔다 — 행 중간을 자르면 숫자/항목명이 분리되는 문제가 표 크기를 줄이는 이득보다 크다고 판단.

### 3. 작은 표(레이아웃용)는 문단처럼 취급 — 구현 중간에 추가된 보정

**처음 설계에는 없었고, 실제 99개 문서로 검증하다가 발견해서 추가한 규칙이다.** DART는 `TABLE` 태그를 진짜 데이터 표뿐 아니라 표지의 "금융위원회 | / 한국거래소 귀중 | 날짜"처럼 순수 텍스트 배치 목적으로도 쓰는데, 이런 표가 문서당 최대 2,000개 넘게 섞여 있다. 처음 구현대로 표를 무조건 독립 청크로 분리했더니 **문서당 청크 수가 중앙값 2,559개**까지 나왔다(원래 기대치는 수십~200개 수준).

**대응**: `small_table_chars`(기본 200자) 미만인 표는 "진짜 데이터 표"가 아니라 레이아웃용으로 보고, 문단과 똑같이 버퍼에 합친다(섹션/크기 경계 규칙도 문단과 동일하게 적용). 이 조정 후 **문서당 청크 수 중앙값이 1,410개로 감소**(-45%), 전체 청크 수는 272,144 → 156,707개로 줄었다. 여전히 최초 기대치보다는 많지만, 이건 예상이 안일했던 것이지 버그가 아니다 — 이 문서들 자체가 재무제표 세부 항목상 표 밀도가 원래 그만큼 높다(EDA 기준 문서당 표 블록이 평균 약 2,000개). 156,707개는 로컬 postgres+pgvector 한 대로 충분히 감당 가능한 스케일이라 추가 튜닝은 하지 않았다.

200자라는 임계값 근거: 실측한 레이아웃용 표(표지 정보 등)가 대략 100~150자대였고, 표 블록 길이 중앙값(81자)보다는 확실히 크게 잡아서 진짜 작은 데이터 표(예: 2x2 요약표)까지 과하게 병합되지 않도록 여유를 뒀다.

### 4. 오버랩은 안 넣는다

섹션 경계로 이미 의미 단위를 나누고 있어서, 문장 몇 개를 잘라 인접 청크에 중복시키는 슬라이딩 윈도우 오버랩은 이 문서 구조에서는 이득보다 복잡도가 커 보인다. 나중에 검색 품질 보고 필요하면 추가.

### 5. 청크 메타데이터

DB 저장을 염두에 두고, 각 청크에 다음을 같이 들고 있는다 (일부는 상위 파이프라인에서 주입):

| 필드 | 예시 | 용도 |
|---|---|---|
| `rcept_no` | `20250311001085` | 원본 공시 식별자 (상위 파이프라인이 주입) |
| `corp_code` / `corp_name` | `00126380` / `삼성전자` | 회사 필터링 (상위 파이프라인이 주입) |
| `section_path` | `["III. 재무에 관한 사항", "2. 연결재무제표"]` | 브레드크럼, 임베딩 인풋 및 LLM 프롬프트 문맥으로 사용 ([docs/embedding_strategy.md](embedding_strategy.md)) |
| `type` | `paragraph` / `table` | 표/텍스트 검색 가중치를 다르게 줄 수도 있음 |
| `chunk_index` | `0, 1, 2, ...` | 같은 섹션 내 순서 (인접 청크를 같이 보여줄 때 사용) |
| `text` | (본문) | 임베딩 대상 + LLM 컨텍스트 |

## 인터페이스

```python
# src/chunking/chunker.py
def chunk_blocks(
    blocks: list[dict],
    target_chars: int = 900,
    table_max_chars: int = 1500,
    small_table_chars: int = 200,
) -> list[dict]:
    """paragraph와 작은 표는 섹션 내에서 묶고, 큰 표는 헤더 유지하며 분할해서 청크 리스트를 만든다."""
```

다음 단계는 이 청크에 `embedding/`([docs/embedding_strategy.md](embedding_strategy.md))로 벡터를 붙여서 `db/`(SQLAlchemy + pgvector)에 저장하는 것.
