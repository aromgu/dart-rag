# dart-rag — 한국 기업 공시 기반 재무 Q&A RAG 시스템

**한 줄 요약**: 한국 DART(전자공시시스템) 사업보고서 99건(15만 6천여 개 청크)을 대상으로, 질문 하나에 근거 문장과 함께 정확한 재무 수치를 답하는 RAG 시스템을 데이터 수집부터 API/웹 배포까지 단독으로 설계·구현했습니다.

[GitHub 저장소](https://github.com/aromgu/dart-rag) · [전체 실험 기록](../docs/experiments.md) · [기술 문서 모음](../docs)

---

## 왜 만들었나

DART 공시는 회사마다 형식이 조금씩 다른 XML/표로 흩어져 있어서, 특정 재무 수치 하나를 찾으려면 수십 페이지짜리 사업보고서를 직접 뒤져야 합니다. 이 문제를 "질문 하나로 정확한 답 + 원문 출처"를 돌려주는 RAG 파이프라인으로 풀었습니다. 매 설계 결정을 "그럴듯해 보이는가"가 아니라 **실제 데이터로 검증**하는 데 집중했고, 이 과정에서 13개의 비교실험을 진행하며 검색/생성 전략을 데이터 기반으로 확정했습니다.

## 핵심 성과

| 지표 | 결과 |
|---|---|
| 처리 규모 | 코스피 시가총액 상위 100개 기업, 사업보고서 99건, 청크 156,707개 |
| 검색 품질 | cross-encoder 재순위 도입으로 recall@5 **67.5% → 77.3%** |
| 최종 답변 정확도 | 프롬프트·컨텍스트 개선으로 **46.7% → 60.0%** (추가 GPU/모델 비용 없이) |
| 검증 체계 | 자체 골드셋 199문항 + 결정론적 사실 정합성 체크(정답 수치가 근거자료에 실제로 있는지 SQL로 직접 대조) |
| 비교실험 | 검색 융합 방식, 재순위, 청킹, 프롬프트 전략 등 13개 실험을 가설→실측→원인분석 순으로 진행 |
| 배포 | FastAPI(비동기, 무상태 멀티턴) + 웹 채팅 UI + GitHub Actions CI |

## 아키텍처

```
DART Open API → 파싱(구조 보존 XML) → 청킹(섹션/표 특화) → 임베딩(bge-m3 dense+sparse)
    → PostgreSQL/pgvector(HNSW) → 검색(가중합 융합 + cross-encoder 재순위)
    → 생성(Qwen2.5-3B-Instruct) → FastAPI → 웹 UI
```

## 기술적으로 어려웠던 지점과 해결 과정

**1. O(n²) 성능 버그로 파싱이 7시간 동안 멈춤**
XML 안의 가짜 태그를 걸러내는 정규식 콜백에서 매 문자마다 전체 문자열을 슬라이싱하고 있었습니다. 한 문서가 예상(20~30분)보다 훨씬 오래 걸리는 걸 프로세스 경과 시간으로 눈치채고, `re.match(string, pos)` 포지셔널 매칭으로 바꿔 해결했습니다.

**2. "검색 전략은 실측 없이는 못 정한다"는 걸 반복해서 확인**
이론적으로 우아한 RRF(Reciprocal Rank Fusion)보다 단순한 정규화 가중합이 실측으로 더 나았고, cross-encoder 재순위도 breadcrumb(회사명/문맥) 없이 텍스트만 넣으면 오히려 성능이 떨어진다는 걸 154문항 골드셋으로 직접 확인했습니다. 같은 "문맥 부재" 문제가 sparse 임베딩, BM25, 생성 컨텍스트(연결/별도재무제표 구분)에서도 독립적으로 재발견되며 일관된 패턴으로 정리됐습니다.

**3. "검색은 맞는데 최종 답이 틀리는" 병목을 end-to-end 실험으로 규명**
검색 recall은 70~80%대인데 최종 답변 정확도는 그보다 낮았습니다. 오답 사례를 SQL로 직접 검산해서 원인이 hallucination이 아니라 "문맥 안의 다른(엉뚱한 연도·계정과목) 숫자를 잘못 고르는 것"임을 확정하고, 프롬프트 체크리스트·표 재포맷·연결/별도 명시 태그·few-shot 예시를 순차 적용해 비용 0으로 정확도를 13%p 이상 끌어올렸습니다. (표를 "읽기 쉽게" 재포맷하는 개선이 오히려 성능을 떨어뜨린 적도 있었는데, 원인을 진단해 명시적 태그로 재반전시켰습니다.)

**4. 인프라 제약 속에서의 실용적 트레이드오프**
GPU/디스크 자원이 제한된 환경에서, 원래 계획했던 7B 생성 모델을 3B로 축소하고, HuggingFace 캐시의 불필요한 리비전을 `strace`로 실제 사용 파일을 추적해가며 정리하는 등, 이상적인 선택과 가용 자원 사이의 균형을 계속 맞춰야 했습니다.

## 기술 스택

**데이터 파이프라인** Python, BeautifulSoup+lxml(구조 보존 XML 파싱, 모델 미사용)
**임베딩/검색** BAAI/bge-m3(dense+sparse), PostgreSQL+pgvector(HNSW), BAAI/bge-reranker-v2-m3
**생성** Qwen2.5-3B-Instruct(HuggingFace transformers, 로컬 GPU)
**서빙** FastAPI(비동기), Tailwind+Flowbite 웹 UI, Streamlit(대안 UI)
**품질/운영** pytest(GPU 비의존), GitHub Actions CI, 자체 평가 프레임워크(Recall@k/MRR + 결정론적 사실 정합성 체크)
